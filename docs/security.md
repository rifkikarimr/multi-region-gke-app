# Security

## Implemented controls

### CI/CD authentication

GitHub Actions uses OpenID Connect and Google Cloud Workload Identity Federation. No service account JSON key is required. The provider accepts only the configured repository on `refs/heads/main`, and the deploy job requests only `contents: read` and `id-token: write` GitHub permissions.

The deployment service account can push images and operate Kubernetes resources through the GKE API. Terraform outputs the provider resource name and service account email; these are identifiers, not credentials, and should be stored as GitHub repository or environment variables.

### Container and Kubernetes runtime

- The image runs as UID/GID `10001`, not root.
- The Pod disallows privilege escalation, drops Linux capabilities, uses the runtime-default seccomp profile, and mounts a writable empty `/tmp` over a read-only root filesystem.
- The application does not receive a Kubernetes service account token.
- CPU and memory requests and limits constrain resource consumption.
- Health probes gate traffic and restart failed containers.

### GKE identity

GKE Workload Identity is enabled. The application has no Google Cloud API dependency, so no Kubernetes-to-Google service account binding is created. Nodes use a dedicated runtime service account with only registry-read and GKE logging/monitoring roles instead of the default Compute Engine identity.

### Secret handling

The repository contains no runtime application secrets. Terraform variable examples contain placeholders only. `.gitignore` excludes local Terraform values/state and temporary credentials generated by the Google authentication action.

GitHub configuration values such as project ID, cluster names, locations, repository name, WIF provider, and service account email are not secrets and should be repository or protected environment variables. Any future confidential values belong in an external secret manager, not Kubernetes YAML, Terraform variable files, or GitHub workflow source.

## Trust model

The trust boundary includes repository administrators, changes merged to `main`, the GitHub Actions runtime, the configured GitHub environment, the WIF provider, and the deployment service account. A protected GitHub `production` environment with required reviewers and branch protection is recommended. Terraform restricts OIDC claims, but GitHub-side protections must still control who can change and run the deployment workflow.

## IAM considerations

The included predefined roles are understandable and practical for a reference project, but they are project-scoped. Before adapting this design to production:

- split build and cluster deployment identities;
- replace predefined project roles with tested custom roles where justified;
- separate environments into projects;
- review who can modify WIF providers, service accounts, repository variables, and workflows;
- retain audit logs and alert on sensitive IAM changes.

## Known limitations

- GKE control-plane public endpoint restrictions are not configured.
- Worker nodes are not private; Cloud NAT is therefore not provisioned.
- Public Services do not include TLS or an authenticated edge.
- Kubernetes NetworkPolicy, admission policy, image signing/verification, vulnerability gates, and secret-manager integration are not implemented.
- CI actions use supported floating major tags rather than immutable commit digests. Major tags receive fixes but can move.
- The example does not manage GitHub branch or environment protection settings.

These are conscious scope boundaries, not claims of secure-by-default production readiness.
